# 프롬프트 2 — 선택 반영 후 보고·제안·계획 승인·실행 시작

권장: sonnet / medium, 코드를 쓰는 작업은 plan 모드로 시작. 설계 판단이 필요한 항목만 `waam-architect`(opus, high). **★2 승인 전에는 파일을 수정하지 않는다.**

먼저 `docs/prompts/_common.md`를 읽고 따른다. 입력 헤더는 이 메시지 맨 위에 있다. 이 메시지에 ★1 답(`D-xx=…`)이 들어 있다.

## 2.0 선택 반영

- ★1 답을 `DECISIONS.md`에 기록한다: 결정 / 보류, 선택지, 일시. (이 기록은 승인 전에 허용되는 유일한 파일 수정이다.)
- 답이 모호하면 **한 번만** 되묻는다.
- 결정에서 생긴 후속 작업(예: `CLAUDE.md` 규칙 추가, 명세 수정)은 실행하지 말고 목록으로 만들어 ★2 계획의 첫 항목으로 포함한다.

## 2.1 현재 보고 — 전체에서 어디까지 왔고 무엇이 남았나

선택을 반영한 뒤 **달라진 것만** 쓴다: 차단이 풀린 작업, 새로 생긴 후속 작업, 남은 일 목록. 변경 / 측정 / 판단 3줄.

## 2.2 현재 제안 — 오늘 가용 자원 안에서 가능한 작업, 그리고 사용자 개입 지점

헤더(가용 시간, 체력, 토큰, 개입)를 입력으로 아래를 낸다.
1. **열 선택**: `docs/handoff.md` §7의 열 ①~⑤ 중 하나를 제안하고 사유 한 줄. 기본값은 그 열의 값이고, 오늘 상황으로 조정한 부분은 명시한다.
2. **작업 큐**: 순서, 등급(A/B/C), 모델·effort, 완료 기준(자동 판정), 중단 조건, 예상 시간(근거: `실측` / `가설`).
3. **사용자 개입 지점**: 시각 순서로 — 언제, 무엇을, 몇 분. 결정이 필요한 것은 **연속 블록(≥1.5h)** 안에 몰고, 10~30분 확인은 보기만 하게 배치한다.
4. **이번에 하지 않을 일**: 우선순위에서 밀린 것을 명시한다.
5. **불안요소와 Plan B**: 사용량 한도, 리뷰어 탐색 시간, 헤드리스·절전 등 해당하는 것.
6. **이상적 계획 / 현실적 계획**: 현실적 계획에는 버퍼를 넣는다. 버퍼의 크기를 정할 근거가 없으면 `가설`로 표시하고 크기를 꾸며내지 않는다.
7. **병렬 가능한 작업**: 있으면 브랜치·worktree 분리 조건과 함께, 없으면 `없음`.
8. **중간 체크포인트**: 계획 중반 시각과 종료 비교 시각.

## 2.3 ★2 결정 구간 — 오늘 계획 승인

`_common.md` §4-2 양식으로 제출한다. B등급 결정이 남아 있으면 §4-1 메모를 같은 구간에 붙인다(합쳐서 최대 3건). 답 형식을 안내하고 **여기서 멈춘다.**

## 2.4 현재 지시 — ★2 답에 따라 실행 시작

- `승인`: 승인된 계획을 `docs/prompts/session-<날짜>.md`로 저장하고, `PROGRESS.md`에 시작 시각을 기록한 뒤 첫 작업을 시작한다.
- `수정 n: …`: 해당 항목만 고쳐 ★2를 다시 제출한다.
- `보류 n`: 그 항목을 큐에서 빼고 `DECISIONS.md`에 보류로 기록한다.
- `취소`: 아무것도 시작하지 않는다.

실행 규칙
- 모듈 흐름: plan 모드 계획 → (승인된 계획이면 바로) 구현 → `waam-reviewer` 리뷰 → 반영 → pytest → 커밋.
- 모듈마다 체크포인트 커밋, 기본 브랜치 직접 커밋 금지.
- 중단 조건은 `_common.md` §5를 따른다.
- 계획 중반 시각에 계획 대비 결과를 한 줄로 `PROGRESS.md`에 남긴다.
