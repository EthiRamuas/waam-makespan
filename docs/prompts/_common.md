# 공통 규칙 — docs/prompts/_common.md (초안)

모든 상황별 프롬프트(`1-기상후.md` `2-선택반영후.md` `3-주간결정.md` `4-자기전.md`, 야간 실행용 `night-template.md`)가 맨 먼저 읽는 파일이다. 규칙의 근거와 값은 `docs/handoff.md`(통합본)에 있다. 이 파일과 통합본이 다르면 **통합본이 기준**이다.

## 1. 입력 헤더

사용자가 메시지 맨 위에 4줄로 준다. 프롬프트 파일에는 슬롯이 없다.

```
가용 시간: __h (연속 블록 __h; 결정용 연속 블록 1.5h 이상 확보: 예/아니오)
체력(내 집중력): 상 · 중 · 하
토큰 잔량: __% (측정 방법: __ / 미확인이면 '미확인')
개입: 상시 | __분마다 확인 | 취침 중(기상 __:__)
```

- 헤더가 없거나 칸이 비어 있으면 **한 번만** 묻는다. 사용자가 없는 세션(야간 실행)은 묻지 말고 `night-<날짜>.md`에 적힌 값만 쓴다.
- 이 4줄은 프롬프트의 종류를 바꾸지 않고 **제안의 크기**를 바꾼다. 가용 시간이 짧거나 체력이 낮으면 후보를 줄이고 B등급 결정 건수도 줄인다.

## 2. 읽는 순서

1. `CLAUDE.md`(자동 로드), 이 파일
2. `PROGRESS.md` → `DECISIONS.md`("결정 대기"와 최근 항목)
3. `docs/handoff.md` §7(열×행 값 표)과 §6(위임 규칙) — 필요한 부분만
4. 필요할 때만 `docs/operations.md`, `docs/spec.md`. `docs/experiments.md`는 **사람이 쓰는 파일이므로 읽기만 한다.**

## 3. 보고 형식

- 모든 보고는 **변경 / 측정 / 판단** 3줄을 포함한다.
- 측정하지 않은 값은 `미측정`. 돌리지 않은 것의 숫자를 추정해서 쓰지 않는다.
- 시간 예상에는 근거를 붙인다: `실측`(handoff.md §8 표의 값) 또는 `가설`(근거 없음). 근거 없는 예상을 단정하지 않는다.
- 확인하지 못한 사실(헤드리스 플래그, 사용량 한도, 알림 수단)은 단정하지 말고 `미확인`과 확인 방법을 적는다.
- 보고는 한 화면 분량을 목표로 한다. 전체 표는 파일 경로로 가리키고 본문에는 요약만 둔다.

## 4. 결정 구간 제출 양식

결정 구간(★1~★4)에서는 **이 양식으로만** 사용자에게 제출한다. 사용자는 답을 한 줄로 쓴다.

### 4-1. B등급 결정 메모 (★1, ★3에서 쓰고 ★2·★4에 포함될 수 있음)

한 구간에 **최대 3건**. 넘치면 데드라인이 임박하거나 다른 결정을 막는 순서로 3건만 올리고 나머지는 `다음 구간`으로 표시한다. 짧은 기간에 많은 결정을 하지 않는다.

```
[D-xx] 제목
 문제 정의: 한 줄
 충족 조건: 이 결정의 답이 만족해야 할 것 (한 줄)
 선택지: a) …  b) …  c) …
 권고: a — 이유 한 줄
 되돌림 비용: 낮음 / 중간 / 높음 — 한 줄
 결정 책임자: 나 / 교수님 / 팀  |  데드라인: …  |  영향 받는 자: …  |  알아야 할 자: …
 무응답 시: 멈춤 (사용자가 있는 시간대는 기본안 진행이 없다)
```

답 형식: `D-07=a, D-08=b, D-09=보류`

### 4-2. ★2 오늘 계획 승인

```
선택된 열: ①~⑤ — 사유 한 줄
| # | 작업 | 등급(A/B/C) | 모델·effort | 완료 기준(자동 판정) | 중단 조건 | 예상 시간(근거) | 내 개입 지점 |
이번에 하지 않을 일: …
불안요소와 Plan B: …
이상적 계획 / 현실적 계획(버퍼 포함): …
중간 체크포인트: __:__ (계획 중반)  |  종료 비교: __:__
```

답 형식: `승인` / `수정 3: …` / `보류 2` / `취소`

### 4-3. ★3 주간 제안 실행 승인

```
제안 작업: # 작업, 등급, 예상 시간(근거)
열: ① ② ③ 중 하나 — 사유
개입 정도와 빈도: 다음 확인까지 __분 / 그 사이 내게 올 결정 예상 __건 / 내가 자리를 비워도 되는 최대 시간 __
```

답 형식: `실행` / `수정: …` / `대기` (지금 못 봄 — 아무것도 시작하지 않는다) / `열 변경: ③`

### 4-4. ★4 야간 할당 승인 (마지막 사람 개입)

```
야간 큐: | # | 모듈 | 명세 위치 | 완료 기준 | 중단 조건 | 의존 | 예상 시간(근거) | 자격 4조건 ✓✓✓✓ |
탈락한 후보와 사유: …
여유분(읽기 전용) 작업: …
떠나기 전 체크리스트(열 ④): 절전 해제 □ / 업데이트 재시작 미룸 □ / 작업 트리 clean □ / 명세·테스트 케이스 승인 □ / 큐 순서 확정 □ / 시작 방식 확인 □
```

답 형식: `승인` / `수정 2: …` / `제외 2` / `취소` — **이 승인 이후에는 사람이 없다.** B등급 결정은 모두 이 앞에서 끝나 있어야 한다.

## 5. 금지와 중단 (공통)

**하지 않는다**
- `C:\Github\WAAM_Validator` 수정, `config.yaml`·`target.stl` 수정, `docs/experiments.md` 수정
- `git push`, 삭제, 기본 브랜치에 직접 커밋(자리 비움 세션은 별도 브랜치)
- 기존 테스트와 골든 fixture 수정 (신규 테스트 추가만 허용)
- 특정 `tests/NN`에 맞춘 하드코딩
- 권한 우회 플래그(`--dangerously-skip-permissions`) 제안·사용
- 사용자 답을 받기 전에 결정 구간 다음 단계로 넘어가기

**멈추고 보고한다**
- 같은 오류로 2회 연속 실패
- 리뷰 반영 후 pytest 실패
- 명세에 없는 결정이 필요해짐 (해당 작업만 보류, 독립 작업은 계속)
- 타임박스 초과, 토큰 95% (측정법이 확인된 경우에 한함 — 미확인이면 체크포인트 커밋을 더 자주)
- 위 금지 행위가 필요해 보일 때

**리뷰어** `waam-reviewer`를 부를 때는 항상 덧붙인다: "무작위 탐색 스크립트는 3분 이내, 샘플 수 상한을 두고 돌려."

## 6. 갱신 의무

- 작업 시작·종료 시각을 `PROGRESS.md`에 즉시 기록한다 (시간 기록은 바로바로).
- 결정은 `DECISIONS.md`에 `상태`(대기 / 결정 / 기본안 진행 / 보류)와 함께 기록한다.
- 체크포인트마다 `PROGRESS.md`에 현재 단계, 통과 테스트 수, 막힌 곳, 다음 작업, 신호 한 줄(계속 / 개입 필요 / 중단 권고)을 갱신한다.
- 재개할 때는 `git log --oneline -8`, `git status`, `pytest -q`를 **먼저** 실행해 상태를 확인한다 (중단된 순간 파일이 반쯤 쓰였을 수 있다).
