## 1. 사용 흐름

1. **열 고르기** — 부재 길이와 사람 개입 가능 여부를 입력해 열(①~⑤)을 고른다.
2. **조정** — 그 열의 값이 기본값이 된다. 오늘 상황(한도, 마감, 야간 PC 가동 가능 여부)으로 조정한다.
3. **세션 계획서** — 조정한 값을 세션 계획서로 돌려받는다.
4. **갱신** — 복귀 후 실제 소요 시간으로 시간볼륨 칸을 갱신한다 (§8).

사용자가 실제로 붙이는 것은 **상황별 프롬프트(§2)** 이고, 열 표(§7)는 그 안에서 기본값을 공급하는 부품이다. 시간대가 정해지면 어떤 칸을 쓸지는 정해져 있으므로 매번 조합을 고르지 않는다.

| 열 | 부재 길이 | 사람 개입 |
|---|---|---|
| ① 단시간 | 10~30분 | 곧 복귀 |
| ② 중시간 | 1~2시간 (오늘 저녁형) | 체크 가능 |
| ③ 종일 부재 | 5시간 이상 (수업 등) | 낮 동안 불가 |
| ④ 야간 | 수면 전 예약 (신규 코드 작성 포함) | 취침 전·기상 후만 |
| ⑤ 사람 있음 | 아침 보고 후 설계, 플래닝 병행 | 상시 |

### 2-5. 공통 헤더 (2차 변수)

시간, 체력, 토큰, 개입은 프롬프트의 종류가 아니라 **입력**이다. 프롬프트를 늘리지 않고, 같은 "오늘 제안"도 입력에 따라 크기가 달라진다. 형식과 처리 규칙은 `prompts/_common.md` §1.

### 2-6. 해석과 한계 (확인 필요)

- **프롬프트 2의 해석.** "새벽 시간대 선택에 따른 진행 후 보고와 결정"을 *★1에서 사용자가 내린 선택을 반영하고 그에 따라 달라진 상태를 보고한 뒤 오늘 계획을 승인받아 실행을 시작하는 단계*로 해석했다. 새벽 세션의 결과 자체는 프롬프트 1이 보고한다. 의도가 다르면 2.0과 2.1만 고치면 된다. **[미확인]**
- **중간 확인.** 기존의 읽기 전용 중간 확인은 프롬프트 3의 `신호만`으로 흡수했다.
- **시작 방식.** 헤드리스 `claude -p` 플래그는 v2.1.291에서 **[미확인]**이다. 지금 확인된 방식은 대화형 auto 세션에 시작 입력을 넣는 것이며 **예약이 아니라 즉시 시작**이다 (E4, K3).
- **검증 범위.** 프롬프트 파일은 이 환경에서 Claude Code로 실행해 보지 못했다. 참조하는 파일 경로, 서브에이전트 이름, 섹션 번호가 서로 맞는지만 스크립트로 확인했다. 첫 실행에서 나온 문제는 §8 시간 기록처럼 §4 결정 로그에 남겨 고친다.

## 6. 위임 규칙

### 6-1. 등급: 결정의 종류로 나눈다

계속 붙어 있어야 하는 이유는 작업 크기가 아니라 **결정이 중간에 끼어 있기 때문**이다.

| 등급 | 기준 | 예 | 방식 |
|---|---|---|---|
| **A 전부 위임** | 완료 기준이 자동 판정(pytest, Validator exit 0)되고 되돌릴 수 있음 | 확정 명세의 구현, 리뷰 반영, 벤치마크, 문서 갱신 | 시작만 하고 결과 확인 |
| **B 준비만 위임** | 선택지와 권고안은 만들되 결정은 사람 | baseline 전략 선택, float32 버퍼, 인터페이스 승인, 탐색 알고리즘 방향 | 선택지·권고안까지 만들고 **멈춤** |
| **C 사람만** | 방향, 해석, 되돌릴 수 없는 일 | 과제 방향·제출물, 팀 합의, 교수님께 질문, push·삭제, "이 결과가 의미 있나" | 건드리지 않음 |

### 6-2. 규칙

1. **되돌릴 수 있는 결정은 기본안으로 진행하고 `DECISIONS.md`에 기록, 되돌릴 수 없는 결정은 멈춘다.** (열 ④는 예외: B등급은 아예 올리지 않는다. A2 확정 전의 **[제안]**)
2. **한 번에 맡기는 4조건 — 모두 맞아야 한다:** ① 완료 기준이 자동 판정된다 ② 되돌릴 수 있다 ③ 중간 결정 지점이 사전에 해결돼 있다 ④ 중단 조건이 명시돼 있다. 하나라도 빠지면 쪼개거나 결정 지점에서 끊는다.
3. **분할 경계:** 결정 지점, 리뷰 게이트, 컨텍스트가 너무 커지는 지점. 단계 사이에 결정이 없고 완료 기준이 자동 판정되면 한 프롬프트로 가도 된다. 프롬프트에는 순서, 단계별 완료 기준, 중단 조건, 보고 형식을 넣는다.
4. **판단이 어려운 것은 설계 쪽이다.** 코드가 틀리면 Validator가 FAIL로 잡지만 설계가 틀리면 아무도 안 잡는다. 그래서 비싼 모델은 "무엇을 만들지 정하는 자리"에 놓는다 (운영 설계 §2-0).

### 6-3. 야간 신규 코드 작성 조건 (2026-10-09 허용 [확정], 조건은 [제안])

사용자가 야간 신규 코드 작성을 허용했다. 이는 기존 문서의 두 문장과 충돌한다.

- 운영 설계 §4-1: "야간은 탐색과 측정만 한다"
- 스크랩본 v1 초안: "12시간(야간)은 코드 신규 작성은 피함"

그 문장들이 막으려던 위험은 **"아침에 검증할 수 없는 결과물을 받는 것"** 이다. 허용하되 이 위험이 남지 않는 범위로 묶는다.

**J-1. 자격 — 아래를 모두 만족하는 모듈만 야간 큐에 올린다**

1. **명세가 확정**돼 있다: 인터페이스·시그니처·단위·테스트 케이스가 세션 계획서에 있고, 사람이 ★4에서 승인했다.
2. **설계 결정이 없다** (A등급). 구현 방법의 선택지가 남아 있으면 B등급이므로 야간에 올리지 않는다.
3. 완료 기준이 **자동 판정**된다 (pytest, 건전성 테스트, Validator exit code).
4. 되돌릴 수 있다 (`nightly/<날짜>` 브랜치 위의 로컬 커밋).

**J-2. 야간에 맡기지 않는 것**

3~4단계 전략 설계(Assigner/Scheduler 본체), 해칭 패턴 등 해공간을 정하는 결정, 실험 결과 해석, 보고서 논증, `config.yaml`·`target.stl`·교수님 레포 수정, push. (운영 설계 §5-2에서 모두 ③ 버킷)

**J-3. 실행 규칙**

- 모듈마다 **체크포인트 커밋**. 언제 중단돼도 복구되게 한다.
- **기존 테스트와 골든 fixture는 수정하지 않는다.** 신규 테스트 추가만 허용. 통과시키려고 테스트를 고치는 것을 막는 규칙이다.
- 리뷰 게이트(`waam-reviewer` opus high, 탐색 3분·샘플 상한)를 통과한 뒤에만 다음 모듈로 간다.
- 모듈 간 의존이 있으면 순차 진행하고, 앞 모듈이 막히면 의존 모듈은 보류한다.
- 명세에 없는 결정을 만나면 해당 모듈을 **보류**하고 `DECISIONS.md`에 B등급 메모를 남긴다. **의존이 없는 다음 모듈만** 계속한다.
- 특정 `tests/NN`에 맞춘 하드코딩 금지 (`CLAUDE.md` 금지 규칙, 리뷰어가 검사).

**J-4. 첫 야간 범위 [제안·가설]**

명세가 확정된 모듈 **최대 2개**. 남는 시간은 읽기 전용 작업(로그 요약, 문서 갱신)으로 채운다. 시간볼륨이 실측 1~3건뿐이라 5시간 세션에 몇 개가 들어가는지는 환산하지 않는다. 야간 기록이 쌓이면 확대한다.

**J-5. 아침 검증 (병합은 사람이)**

순서: 보고 3줄 → pytest·Validator 숫자 → 리뷰 지적의 반영/미반영 목록과 이유 → 결정 대기 → diff 통계 → **신규 코드 diff를 직접 훑기**. 병합 전 확인: 리뷰 통과 + pytest 통과 + 기존 테스트·fixture 변경 없음.

> 야간 신규 모듈 수의 상한이 곧 아침 검증량이다. 무인 자동화가 좋아질수록 마지막에 투입되는 사람이 상태를 파악하기 어렵다는 점(R42)이 근거다.

## 7. 열 × 행: 고려 항목과 기본값

### 7-1. 뼈대: 행(고려 항목) 정의와 입력 순서

행들 사이에는 **의존 순서**가 있다. 개입 정도(위임 등급)를 먼저 정하면 모델·추론량이 따라오고, 체크 주기는 그 위험도에 맞춰 정해진다. 입력은 아래 순서로 한다.

| 순서 | 행 | 이 행이 정하는 것 | 관련 질문 |
|---|---|---|---|
| 1 | **개입 정도** | 무엇을 누가 결정하나 (A/B/C, B등급 처리 방식) | A1 A2 A3 |
| 2 | **목적** | 이 세션이 끝났을 때 달라져 있어야 하는 것 | F2 F3 |
| 3 | **맡길 작업** | 작업 큐와 각 작업의 등급·완료 기준 | A1 A4 J1 |
| 4 | **모델** | 작업 종류별 모델 | C1 |
| 5 | **추론량** | 작업 종류별 effort | C1 |
| 6 | **시간볼륨** | Claude가 해야 할 **총 작업량**과 그 예상 시간 | B1 B3 B4 |
| 7 | **시간 연속성** | 사람 없이 끊김 없이 갈 수 있는 구간 / 사람이 확보해야 하는 연속 블록 | B2 |
| 8 | **체크 주기** | 사람이 들여다보는 간격과 방법 | B2 E5 |
| 9 | **중단 조건** | 멈추고 보고해야 하는 상황 | D1 D2 |
| 10 | **복귀 시 확인물** | 돌아와서 무엇을 보면 되나 | F5 |
| 11 | **떠나기 전 사람이 할 일** [신규] | 이게 빠지면 세션이 시작도 못 하거나 중간에 죽는 준비 | I1 E2 E4 |

> 시간볼륨과 시간 연속성은 정의를 갈라서 쓴다. 볼륨은 *얼마나 일하나*, 연속성은 *끊김 없이 갈 수 있나*이다.
> 칸 값은 §7-2에 있다. 값 옆의 태그([실측] [가설] [확정] [미확인])를 지우지 말 것.

### 7-2. 열 × 행 값 표 (기본값)

열 = 부재 길이 × 사람 개입 가능 여부. 칸 = 그 고려로 예상·배분한 기본값. 오늘 상황으로 조정해 쓴다. 입력 순서(§7-1)는 개입 정도 → 목적 → 맡길 작업 → 모델 → 추론량 → 시간볼륨 → 시간 연속성 → 체크 주기 → 중단 조건 → 복귀 시 확인물 → 떠나기 전 할 일.

| 행 \ 열 | ① 단시간 (10~30분) | ② 중시간 (1~2시간) | ③ 종일 부재 (5h+) | ④ 야간 (수면 전 예약) | ⑤ 사람 있음 |
|---|---|---|---|---|---|
| **개입 정도** | A, B는 즉답 | A + B(기본안 진행·기록) [제안] | A 위주, 사전 해결된 B만 | **A 전용**, 사전 승인된 명세만 [제안] | B, C |
| **목적** | 작업 하나 마무리 | 모듈 2~3개 연속 | 단계 하나 진행 | 아침에 숫자·테스트로 판정할 수 있는 결과 (신규 코드 포함) | 결정, 설계, 다음 구간 배분 |
| **맡길 작업** | 단일 작업, 확정된 구현 | 구현 → 리뷰 → 커밋 반복 | 사전 결정이 끝난 단계 (설계는 맡기지 않음) | 확정 명세 모듈 신규 구현(조건 J), 벤치마크·스윕, 로그 요약 | B등급 결정, 3~4단계 설계, 명세 작성 |
| **모델** | sonnet | 구현 sonnet, 리뷰 opus | 구현 sonnet, 리뷰 opus, 요약 haiku | 구현 sonnet, **opus는 리뷰 게이트만**, 요약 haiku | opus (설계는 틀리면 복리로 쌓임) |
| **추론량** | medium | 구현 medium, 리뷰 high | 구현 medium, 리뷰 high | 구현 medium, 리뷰 high | high |
| **시간볼륨** | 모듈 1개도 빠듯 **[실측]** 계획~커밋 약 40분(사람 대기 포함) | 모듈 2~3개 **[가설]**. 리뷰어 4.5~31.9분 변동 **[실측]** | **[가설]** 실측 후 확정 | 세션 5시간은 사용자 계획 **[확정]**, 작업량 **[가설]**. 첫 야간 최대 2모듈 **[제안]** | 사람 시간이 병목 |
| **시간 연속성** | 사람이 곧 복귀, 대화형 | 모듈 사이 리뷰 게이트에서 끊김 | 사람이 개입 못 하는 긴 블록 | 완전 무인 블록. 결정은 ★4 이전에 모두 끝나 있어야 함 | 사람의 연속 블록 **1.5시간 이상** 확보 |
| **체크 주기** | 10~30분에 1회 (보기만) | 30~45분 | 60~90분 (알림 수단 **[미확인]**) | 취침 전 1회 + 기상 1회 | 상시 |
| **중단 조건** | 같은 오류 2회 연속 | + 리뷰 반영 후 pytest 실패 | + 시간 상한 | + 타임박스 초과 + 명세 밖 결정(보류) + 토큰 95%(측정법 **[미확인]**) | 해당 없음. 결정 목록을 비우면 ③·④로 전환 |
| **복귀 시 확인물** | `git log --oneline -5` | git log, PROGRESS.md, DECISIONS.md 결정 대기 | 같음 + 브랜치 diff | 아침 5분 triage (§6-3 J-5) | 결정 대기 비우기 |
| **떠나기 전 사람이 할 일** | 커밋 상태 정리 | 작업 트리 clean, 브랜치 생성, 계획 승인 | + 절전 해제 | + 절전 해제·업데이트 재시작 미루기, `nightly/<날짜>` 생성, 명세·테스트 케이스 승인, **큐 순서 확정(여유분 포함)**, 헤드리스 플래그 확인(첫 회), 신뢰 수락 사전 완료 | 오늘 연속 블록 확보, 결정 대기 사전 정리 |

**이전 표에서 바꾼 점**

- ③의 모델에서 "설계 opus"를 뺐다. 사람이 없는 구간에 설계를 맡기면 4조건 중 ③번(중간 결정 사전 해결)과 모순된다. 설계는 ⑤에서 한다.
- ④의 맡길 작업·개입 정도·모델·중단 조건·떠나기 전 할 일을 신규 코드 허용(D-05)에 맞게 고쳤다.
- 시간볼륨 실측 범위를 진행 현황의 최신 값(리뷰어 4.5~31.9분)으로 갱신했다.
- "떠나기 전 할 일" 행을 추가했다 (야간·종일 부재에서 빠지면 세션이 시작도 못 하거나 중간에 죽는다).

## 9. 모델과 effort (표 하나로 병합)

| 작업 | 모델 | effort | 이유 |
|---|---|---|---|
| 확정 명세의 구현, 리팩토링, 테스트 작성 | sonnet | medium | 양이 많고 판정이 기계적 |
| 설계·전략·알고리즘 판단(3~4단계), 결과 해석 | opus (`waam-architect`, plan 모드) | high | 틀리면 되돌리는 비용이 큼. 사람이 있을 때만 |
| 코드 리뷰 | opus (`waam-reviewer`) | high | 실제 반례를 잡은 사례. **자리 비움 때 건너뛰지 않음 (K5)** |
| 로그·결과 요약, 문서 갱신 | haiku | low | 해석이 필요 없는 일 |
| 단축키·명령어 확인 같은 단순 질문 | 낮은 모델 / 낮은 effort | — | opus가 값을 하지 않는 구간 |

opus + 높은 추론이 값을 하는 지점: ① 이 계획을 스킬·문서로 **굳힐 때**(한 번 만들면 이후 모든 세션에 복리로 적용) ② 3~4단계 알고리즘 설계 ③ 리뷰. 별칭(`opus` `sonnet` `haiku`)을 쓴다.

1. §13의 빈 질문에 대한 **비판적 점검**: 빠진 위험과 중단 조건, 특히 야간 신규 코드의 위험
2. 1~4단계 **배분표** (작업, 등급, 모델, effort, 완료 기준, 중단 조건, 사전 결정 필요 사항). 시간 추정은 실측으로 보정
3. 열별 **운영 절차** + **자리 비움 폼**(§14-2) + **세션 계획서**(§14-3)
4. `PROGRESS.md`, `DECISIONS.md` 구조와 `/waam-handoff` 스킬 초안 (필드는 §12-2)
5. 확정본을 프로젝트 문서로 저장하고 `Claude Code 운영 설계`와 중복되는 부분 정리 (개정 필요 목록은 §15)

진행 방식: 문서를 먼저 읽고, 비워 둔 칸이 있으면 **최대 3개만** 되묻고, 그다음 산출물을 한 번에 초안으로 보여 준다. 이미 있는 내용과 겹치면 새로 만들지 말고 확장한다.

일정 템플릿(가용 시간 → 목표 → 우선순위 → 불안요소 → 연속 시간 → Plan B → 세부 시간 예측 → 이상적/현실적 계획 → 시간 기록 평가 → 개선 → 방향 검토)을 폼과 계획서로 나눠 쓴다. 🅓는 드러커 노트에서 온 필드다.
